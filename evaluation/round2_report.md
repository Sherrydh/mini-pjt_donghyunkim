### 같은 코드를 반복 측정해서 알게 된 것
- **RAGAS 지표는 회차 간 편차가 ±0.01 수준으로 작다.** 그래서 v9 → v12 의 차이는 실제 변경 효과로 봐야 한다.
  - answer_relevancy −0.08, context_recall −0.13, faithfulness −0.05, context_precision +0.14.
  - 중간 분석에서 "버전 간 차이가 실행 변동 안에 있다"고 판단한 적이 있는데, 통과 건수(18~20)에만 맞는 말이었고 RAGAS 에는 틀린 판단이었다.
- **통과 건수는 회차마다 18~19 로 흔들린다.** 케이스 단위 판정이 경계에 걸리는 경우가 있기 때문이다(#9: 3회 중 1회 실패).
- **v12 를 최종으로 고른 이유**: 지표 일부를 내주더라도, 사용자 대화에서 드러난 행동 결함을 모두 고친 버전이기 때문이다.
  - 추천 곡 등급 누락
  - 수준을 말했는데 "모른다"고 답함
  - 궁금한 곡을 '연습 중'으로 저장 제안
  - "체르니 100번이면 충분히 쇼팽을 시작할 수 있다" 같은 근거 없는 판단
  - 이 결함들은 단발형 20건에는 거의 드러나지 않고, 대화형 평가(§6)와 실제 사용에서 드러났다.
- **v9 대비 recall·answer_relevancy 하락의 원인은 아직 분해하지 못했다.** 유력한 가설은 두 가지다.
  - 추천 질문마다 대응 기준 문서가 근거로 들어와, reference 와 다른 근거가 contexts 를 차지한다.
  - 곡별 등급·단계별 경로가 붙으며 답이 길어져 질문 초점이 흐려진다.
  - 남은 과제로 기록한다(§8).

### 되돌린 시도 (v4~v7)
- answer_relevancy 와 #16 장황함을 프롬프트(핵심 답 먼저, 600자 제한, asked/supporting 분리, 적응형 길이)로 고치려 했다.
- 6~8건 표본에서는 좋아 보였지만, 20건 전체에서는 faithfulness 0.935→0.738, context_recall 0.877→0.647 로 근거 충실도가 무너져 되돌렸다.
- 고정 길이 제한(600자)은 여러 항목을 묻는 질문에 맞지 않았다(사용자 지적).

### HITL 구조를 바꾼 이유 (v8 → v9)
- **v8 의 되묻기 interrupt 는 이점이 작았다.** 재개하면 planner 부터 다시 계획해서 "새 질문으로 다시 보내기"와 거의 같았다. 한 번 묻고 끝나 이어지는 대화가 안 됐고, 같은 사용자에게 매번 다시 물었다.
- **v9 의 구조**:
  - **되묻기**: 일반 대화 턴으로 바꿨다(thread 체크포인터).
  - **장기 기억**: 학습 프로필(LangGraph Store)로, 이미 아는 정보는 되묻지 않는다.
  - **HITL**: 사용자 데이터를 바꾸는 행동, 즉 **프로필 저장에만** 승인을 받는다.

## 7. 인-아웃 세트(`test_queries.csv`) 자체의 한계
