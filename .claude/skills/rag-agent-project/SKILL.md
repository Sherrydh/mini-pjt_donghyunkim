# RAG 에이전트 프로젝트 — 스펙 우선 개발 플레이북

한 번의 실제 프로젝트(성인 피아노 독학자용 RAG 에이전트, 이틀 마감 과제)에서 효과가 있었던 진행 방식과,
시간을 잃게 만든 실수를 정리한 스킬이다. 도메인이 달라도 같은 흐름을 쓴다.

핵심 생각은 세 가지다.
1. **무엇을 만들지 먼저 정한다.** 스펙(SERVICE.md)과 평가 세트가 프롬프트·도구·평가 스크립트의 입력이 된다.
2. **점수가 바뀌면 원인이 에이전트인지 평가기인지부터 가른다.** 평가기 결함을 고치지 않으면 개선 효과를 측정할 수 없다.
3. **실험은 버전으로 남기고, 결론은 반복 측정으로 낸다.** 한 번 돌린 점수 차이는 잡음일 수 있다.

**사례를 옮기지 말고 교훈을 옮긴다.** 이 스킬의 예시(체르니, K.545, Henle 등급, 피아노 문서)는 원래 프로젝트의 것이다.
사용자의 도메인이 다르면(헬프데스크 FAQ, 사내 규정 등) 그 도메인의 말로 바꿔 설명하고, 피아노 사례는 사용자가 이 프로젝트를 물을 때만 꺼낸다.
예: "사용자 표현 ↔ DB 기준 브리지 문서" → 헬프데스크라면 "사용자가 쓰는 증상 표현 ↔ FAQ의 공식 오류명 대응표".

## 사용자와 일하는 방식

- 사용자는 한국어로 대화하고, 개념을 자주 되묻는다("planner가 뭐야?", "answer_relevancy는 정확히 뭐야?").
  질문을 받으면 **실제 데이터(케이스 번호, 노드별 입출력, 점수)로 예를 들어** 설명한다. 추상 설명만 하지 않는다.
- 사용자는 내 판단을 검증한다("그런 규칙이 있던가?", "HITL을 이런 용도로 쓰는 게 맞아?", "이 csv는 제대로 된 거야?").
  내가 임의로 넣은 규칙이면 그렇다고 인정하고, 근거를 대며 되돌린다. 방어하지 않는다.
- 구조 변경 제안(예: Supervisor 멀티에이전트)이 실패 원인에 맞지 않으면 비용·위험·평가 영향과 함께 대안(planner 노드)을 권한다.
  사용자는 "적절하지 않으면 안 해도 돼"라고 열어 두는 편이다.
- 커밋·push·배포·공개 게시는 사용자가 요청할 때만 한다. 저장소는 public이므로 `.env`, 회사명·사내 문구, 개인정보를 넣지 않는다.
- 진행 기록은 `history.md`에 날짜·단계·결정 이유·수치로 남긴다. 사용자가 나중에 "왜 그렇게 했지?"를 찾는다.

## 단계별 흐름

### 1. 기획 (인터뷰 → 스펙)
- 아이디어가 모호하면 인터뷰(예: ouroboros interview)로 사용자·유스케이스·코퍼스·범위 정책·완성 기준·스택을 확정한다.
- 인터뷰 다음 단계(seed 등)를 건너뛰지 않는다. 사용자가 "지금 seed 단계 맞아?"라고 물었을 때야 생성한 적이 있다.
- **SERVICE.md를 코드보다 먼저** 쓴다: 사용자·문제(한 문장)·대체 수단·가치, 확장성, 도구·데이터(실제/가짜 명시),
  가드레일 3~5개, 측정 가능한 성공 기준(통과율, guardrail 100%, RAGAS 목표, 도메인 지표).
- 범위 정책은 "균형형"이 잘 통했다: 인접 주제는 제한 답변, 다른 영역은 거절 + 대체 안내, 건강·법률은 진단 없이 전문가 권고,
  저작권 원문은 거절 + 합법 출처 안내, DB에 없는 항목은 "자료 없음"(지어내지 않음).

### 2. 인-아웃 세트 (test_queries.csv)
- positive 40% / negative 20% / edge 25% / guardrail 15%, 15~20건.
- **실수: 코퍼스보다 먼저 써서 근거로 만족할 수 없는 기대 항목이 생겼다(20건 중 5건).**
  세트를 쓴 뒤 데이터를 만들면, 각 케이스의 expected_traits가 코퍼스로 실제 충족 가능한지 한 번 대조한다.
  주관적 기준("간결함", "적절한 길이")은 측정 가능한 형태로 바꾼다.
- 되묻기 기능이 있으면 **"되묻지 말아야 할 명확한 질문"** 케이스도 넣는다. 모호한 질문만 넣으면 과잉 되묻기(뭐든 되물음)를 잡지 못한다.
- 결과를 본 뒤 기준을 고치면 "점수를 맞추려 기준을 옮겼다"로 보인다. 평가 후 발견한 결함은 수정하지 말고 **한계로 기록**하거나,
  고칠 거라면 v2 세트로 변경 이력을 공개하고 이전 결과도 재채점한다.

### 3. 데이터
- 공개 자료(Wikipedia 요약 + URL + 라이선스) + 직접 검수한 "(자체 작성)" 섹션. frontmatter에 doc_id·title·source·license.
- 수치 데이터(난이도 등)는 **확인 가능한 공식 출처만** 넣고, 확인 못 한 항목은 빼는 편이 환각을 막는다.
- 사용자 표현(예: "체르니 100번")과 DB 기준(예: Henle 등급)을 잇는 **대응 기준 문서**가 없으면 에이전트가 수준 질문에 답하지 못한다.
  사용자 언어 ↔ 데이터 기준을 잇는 브리지 문서를 초기에 만든다.
- 문서·DB 구축은 서브에이전트 병렬로 빨리 끝낼 수 있다.

### 4. 구현
권장 그래프와 노드별 역할은 `references/architecture.md`에 있다. 요약:
`guard → load_profile → planner → (ask_user | prefetch → agent ⇄ tools → check → finalize) → propose_memory → approve_memory(interrupt)`
- 응답은 과제 계약 `{answer, contexts:[{doc_id,text}], trace:[{step,input,output}]}`를 지키고 필드를 덧붙이기만 한다.
- 모델 ID·리전은 env로 빼고, **평가에 쓴 모델과 코드 기본값을 일치**시킨다(나중에 "테스트를 Haiku로 했는데 기본값이 Sonnet"인 걸 발견했다).
- Bedrock은 adaptive retry를 켜고, 일일 한도 소진에 대비해 `global.` 추론 프로필 경로를 알아 둔다.

### 5. 평가
상세는 `references/evaluation.md`. 꼭 지킬 것:
- 평가 스크립트에 **케이스별 중간 저장**과 `--tag`, `--rejudge`(저장된 답 재채점), `--ids` 옵션을 처음부터 넣는다.
- 1차 실패를 **에이전트 문제 / 평가기 문제**로 분류한 리포트를 쓴다. 평가기를 고치면 **1차 답을 재생성하지 말고 재채점**해 기준선을 맞춘다.
- judge에는 에이전트가 본 contexts를 함께 주고 "제공된 근거로만 판정, 사전 지식으로 반박 금지, 출처는 표기 여부만"을 명시한다.
- judge가 불통과를 주면 **판정 근거를 contexts와 대조**한다: 답에 단 URL·수치가 contexts에 실제로 있었으면 평가기 오판, 없었으면 답변 쪽 환각이다.
- 한국어 답이면 RAGAS의 질문 역생성 언어와 부분 근거 판정을 보정한다.
- RAGAS는 근거로 답하는 케이스(positive·edge)에만 계산한다. negative·guardrail의 거절 답변을 넣으면 지표가 의미 없이 떨어진다.
- judge를 서비스와 같은 모델로 쓰면 자기 답에 후할 수 있다(self-preference). judge를 라운드 간 고정하고, 통과 케이스 몇 건은 사람이 직접 확인한다.
- 최종 버전은 **3회 반복 측정**해 평균·편차로 보고하고, 대표 파일은 선별 없이 1회차로 고정한다.

### 6. 개선 루프
- 실패 원인별로 조치한다(도구 미호출 → planner 의도별 필수 도구 + check 재요청, 검색 누락 → coverage 쿼리 + prefetch,
  precision 하락 → 리랭킹 + 인용 근거만 반환).
- 버전마다 결과 파일을 `results_round2_vN_<설명>.json`으로 남기고 리포트에 버전 표를 만든다. 라운드 = 코드 버전, 재채점·모델 교체 = 태그.
- 프롬프트 실험이 지표를 떨어뜨리면 되돌린다(v4~v7 길이·must_cover 실험은 faithfulness·recall을 깎아 모두 되돌렸다).
- 내가 근거 없이 넣은 제약(예: "600자 이내")은 실패 원인이 되기 쉽다. 규칙을 넣기 전에 스펙·사용자 요구에 근거가 있는지 확인한다.

### 7. 제출 전 정리
체크리스트는 `references/delivery.md`. 요약: 회사·개인 흔적 제거, 미사용 참고 코드 삭제, 최신 다이어그램만 유지,
비공식 결과는 `evaluation/archive/`로 이동 후 문서 경로 갱신, README 줄 번호 재확인, `run.sh`(LF 고정), pytest 통과, 시크릿 미추적 확인.

### 8. 배포 (선택)
처음 배포하는 사용자에게는 Streamlit Community Cloud가 가장 쉽다. 절차·주의점은 `references/delivery.md`의 배포 절.

## 자주 한 실수 Top 10 (상세: `references/pitfalls.md`)

1. 평가 세트를 코퍼스보다 먼저 써서 충족 불가능한 기대 항목이 생김 → 세트-코퍼스 대조
2. judge가 contexts 없이 사전 지식으로 채점해 정답을 오판 → judge에 contexts 제공
3. RAGAS answer_relevancy가 한국어 답에 영어 질문을 역생성 → 언어 힌트
4. 근거 없는 길이 규칙을 임의로 추가 → 스펙에 없는 제약 금지
5. HITL을 "모호한 질문 되묻기"에 씀(재개 시 계획부터 다시, 이점 작음) → HITL은 되돌리기 어려운 쓰기(저장) 승인에만
6. 승인 대기 중 새 질문 → 옛 승인 카드가 엉뚱한 제안을 승인 → 제안 ID + 만료 응답 + 화면에서 카드 비활성화
7. 평가 도중 노트북 종료로 결과 유실 → 케이스별 중간 저장
8. 단일 실행 점수 차이를 효과로 해석 → 3회 반복 측정으로 편차 확인
9. 평가 모델과 코드 기본 모델 불일치 → config 기본값 = 공식 평가 모델
10. 문서 수정 후 README 줄 번호·파일 경로가 어긋남 → 제출 전 grep 대조
