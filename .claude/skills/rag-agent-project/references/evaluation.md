## 1. 평가 스크립트 기본 기능 (처음부터 넣는다)

- `--round N --tag <이름>` → `results_roundN_<tag>.json`. 라운드는 에이전트 코드 버전, 태그는 재채점·모델 교체·반복 회차.
- `--ids 7,8,12`: 일부 케이스만 실행.
- `--rejudge <파일>`: 답변을 다시 만들지 않고 저장된 답을 새 평가기로 재채점.
- `--rescore-ragas`: RAGAS만 재계산.
- 케이스마다 `*.inprogress.json`에 중간 저장(노트북을 닫아 평가가 유실된 적 있음). 오류는 로그에 남긴다.
- judge·RAGAS 버전 상수(JUDGE_VERSION, RAGAS_VERSION)를 결과 파일에 기록해 어떤 평가기로 나온 점수인지 추적한다.
- judge 모델은 라운드 간 고정. 기본값을 서비스 모델과 같은 경로(`global.` 등)로.
- 통과 기준: expected_traits 전부 충족 AND forbidden 0건 AND expected_tools가 trace에 모두 등장.

## 2. LLM-as-judge 설계와 결함

실제로 겪은 오판:
- **J1 출처 권위 판정**: Wikipedia URL을 달았는데 "교재가 아니라 신뢰할 수 없다"며 '출처 표기' 불충족 처리.
- **J2 사전 지식으로 DB 값 반박**: DB·contexts에 있는 등급을 judge가 "그 곡은 그 난이도가 아니다"라며 근거 없음 처리.

judge v2 규칙:
- 에이전트가 받은 contexts(+ 출처 URL)를 judge 입력에 함께 준다.
- "제공된 근거 기준으로만 판정, 사전 지식으로 반박 금지".
- "출처는 표기했는지만 판정(권위 판단 금지)".

불통과 판정을 받으면 고치기 전에 원인부터 가른다:
1. judge의 판정 이유를 읽는다("출처 신뢰 불가", "근거 없음" 등).
2. 답에 나온 URL·수치·고유명이 그 케이스의 contexts에 실제로 있었는지 확인한다.
3. 있었다 → 평가기 오판(J). 없었다 → 생성기가 지어낸 것(A, 환각). 둘은 고칠 곳이 정반대다.

judge 편향:
- 서비스와 같은 모델을 judge로 쓰면 자기 문체에 후할 수 있다(self-preference). 모델을 바꾸면 라운드 비교가 깨지므로,
  judge는 고정하고 통과 판정 3~5건을 사람이 직접 읽어 보는 것으로 보완한다. 리포트에 judge 모델을 적는다.

평가기를 고치면 **1차 답변을 재생성하지 말고 저장된 답을 재채점**해 1차 기준선을 다시 만든다.
그래야 2차 개선폭이 에이전트 효과만 반영한다.

## 3. RAGAS 보정 (한국어)

- **answer_relevancy**: 답에서 질문을 역생성 → 원 질문과 임베딩 유사도. 한국어 답인데 영어 질문을 만들어 점수가 폭락(0.41).
  역생성 프롬프트에 "질문과 같은 언어로" 힌트를 준다. 구어체 질문 vs 격식체 역생성 질문은 Titan 임베딩에서 유사도가 낮게 나오는 측정 한계가 남는다.
- **context_precision**: 근거가 정답의 일부만 뒷받침해도 0점 처리 → "일부라도 뒷받침하면 useful" 힌트.
  근거 순서도 점수에 영향을 준다(보조 검색 결과가 늘 맨 앞에 쌓였다) → 리랭킹 순서를 그대로 contexts에 반영.
- **계산 대상**: 근거로 답하는 케이스(positive·edge)만. negative("자료 없음")·guardrail(거절) 답변은 contexts와 무관한 게 정상이라
  넣으면 faithfulness·relevancy가 의미 없이 떨어진다. 제외한 사실과 대상 건수를 리포트에 적는다.
- 추천형 질문은 정답이 여러 개라 recall·precision이 구조적으로 낮다. 리포트에 명시한다.
- Python 3.14에서 ragas 설치 실패(scikit-network wheel 없음) → 의존성만 빼고 `--no-deps` 설치 + vertexai import shim.
  requirements.txt에는 주석으로 두고 README에 설치법을 적는다.
- 평가기 버전을 바꾸면 1차 포함 모든 결과를 재계산해 같은 평가기로 비교한다.

## 4. 실패 분석 리포트 형식 (round1_report.md)

1. 결과 요약 표: 항목 / 결과 / 목표 / 상태 (통과율, 카테고리별, RAGAS 4지표, 응답 시간)
2. 케이스별 표: id / category / route / 호출 도구 / PASS·FAIL / 실패 원인 코드
3. 실패 원인 분류:
   - A(에이전트): A1 도구 미호출, A2 검색된 근거 누락, A3 장황함 …
   - J(평가기): J1, J2 …
   - R(RAGAS 지표별 원인)
4. 2차 개선 계획 표: 원인 → 조치 → 기대 효과(대상 케이스)

## 5. 버전 관리와 공식 버전 결정

- 버전마다 무엇을 바꿨는지, 통과 수, RAGAS 4지표를 round2_report의 버전 표에 남긴다.
- 지표를 떨어뜨린 실험은 되돌리고 그 사실도 기록한다(실패한 실험도 회고 자료).
- "가장 좋은 버전"은 점수만 보지 않는다: 점수 최고 버전(v3)은 크래시 버그와 기능 누락이 있었고, 결함을 다 고친 버전(v12)을 공식으로 했다.
- 공식 버전은 **같은 코드로 3회 측정**. 회차 간 RAGAS 편차(±0.01 수준)를 보고, 버전 간 차이가 그보다 크면 실제 효과로 본다.
  (편차를 재기 전에 "변동 범위 안"이라고 단정했다가 바로잡은 적 있음)
- 대표 결과 파일은 좋은 회차를 고르지 말고 1회차로 고정, 3회 집계 파일 별도.
- 할당량 소진 등으로 오류가 난 실행은 `_INVALID_quota`로 이름을 바꿔 무효 표시. 제출 전에는 archive로 이동.

## 6. 도메인 지표 (SERVICE.md §5)

SERVICE.md에 정의만 하고 측정하지 않은 지표가 채점상 가장 큰 공백이었다. 결정론적 스크립트로 측정한다:
- 환각 지표: 답변 속 "작품 (등급 N)" 쌍을 정규식으로 추출 → DB 값과 대조.
  오판 방지: 같은 작품번호의 다른 곡(문맥 단어로 구분), 하이픈 표기 정규화, 같은 절 안에서만 짝짓기(fallback 짝짓기 금지).
- 출처 표기율: 근거를 쓴 답변 중 출처를 단 비율.
- 측정 스크립트 자체의 오판을 먼저 샘플로 확인하고 고친 뒤 수치를 보고한다.

## 7. 지표 설명하는 법

사용자가 "X가 정확히 뭐야, 왜 낮아?"라고 물으면:
1. 계산 방식을 한 문단으로.
2. 실제 케이스 하나의 입력·중간값·점수를 보여 준다.
3. 낮은 원인을 에이전트 원인 / 측정 한계로 나눈다.
4. 고칠 방법을 1~3개 제시하고 어느 쪽을 권하는지 말한다.
